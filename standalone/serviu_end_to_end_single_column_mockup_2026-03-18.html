How one procurement task moves through the agent

This page shows one real example from case 48-39-LQ25. The task is to determine whether the bidder accredited digital technical-inspection capability. The flow shows what the agent does at each step: read the public rule, choose a review path, pull the decisive documents, compare them, and write a packet for a human reviewer.

2

2
Read the public rule for this selected task
rule recovery
The agent now follows the selected task branch, reads the public evaluation record for this criterion, and extracts the scoring event. Its job in this step is to turn one page into a usable task rule.
Input artifact
This page names the criterion and states the scoring event: `100` if the bidder accredits the software, `0` if it does not.
What the agent now understands from this page
1
The job is to judge one specific criterion The page is about digital technical-inspection capability as a defined procurement criterion.
2
The scoring event is binary This task closes at `100` if the capability is accredited and at `0` if it is not.
3
The next step is to look for proof in the bidder files The agent now knows it needs documents that show this exact capability, not a general technical claim.
3
Choose the review path
task routing
The agent reads the rule object and classifies the task. Its job in this step is to choose the right review procedure for this criterion.
Input features the agent detects
{
  "criterion_title":
    "seguimiento digital fiscalización técnica de obras",
  "score_shape": [100, 0],
  "requires_narrative_rubric": false,
  "requires_counting_or_banding": false,
  "requires_document_accreditation": true,
  "supporting_files_present": [
    "Anexo 7",
    "API matrix",
    "technical sheets"
  ]
}
How the agent reasons about the route
1
The agent sees a pass/fail documentary task The public rule asks whether the bidder accredited one capability, not how well a narrative proposal was written.
2
The agent sees supporting files it can test against the claim Annex 7 is present, and the technical bundle also includes the API matrix and related support files.
3
The agent chooses documentary verification This route matches the job because the task turns on documentary proof tied to one capability claim.
Documentary verification
The agent selects this path because the task is a binary `100/0` document-accreditation check with supporting technical files.
selected
Proposal review
The agent rejects this path because no scored narrative section appears in the public rule for this criterion.
not used
Count-and-band scoring
The agent rejects this path because the rule does not ask for years, staff counts, project counts, or declared values to be placed into score bands.
not used
4
Pull the bidder’s main claim
evidence recovery
The agent searches the bidder bundle for the first decisive document. Its job in this step is to find the page where the bidder explicitly claims to have the capability.
Input artifact
Annex 7 is the bidder’s public declaration for this criterion.
How the agent reasons through this page
1
The agent looks for a direct statement of the capability This step is about finding the bidder’s own claim, not yet checking whether the claim is well supported.
2
The agent checks whether the page names the right object The useful claim has to name digital technical inspection specifically and tie it to the bidder’s software capability.
3
The agent extracts the claim as a citable object Once the page states the capability clearly, the agent saves the exact claim and its citation for later comparison.
Agent output
{
  "source_path": "offers/.../04_Anexo_7.pdf",
  "claim_excerpt":
    "cuenta con Software de gestión para la Inspección Técnica de Obra Digital",
  "api_declared": true,
  "json_output_declared": true,
  "citation": "04_Anexo_7.pdf#p1"
}
5
Pull the supporting technical file
support check
The agent now looks for a second document that backs up the claim in Annex 7. Its job in this step is to find technical support that can be matched to SERVIU’s requirements.
Input artifact
This public file links SERVIU-required data fields to named software modules.
How the agent reasons through this file
1
The agent looks for a support document that tests the claim The agent looks for technical evidence that can be matched against SERVIU’s requirements.
2
The agent checks whether the file maps requirements to concrete modules A useful support file has to connect named SERVIU data requirements to specific system components or outputs.
3
The agent turns the table into evidence it can compare later It extracts the rows and key matches so the closure step can test whether the supporting file really backs the claim.

6
Compare rule and evidence
closure check
The agent now compares the rule from step 2 to the evidence recovered in steps 4 and 5. Its job in this step is to decide whether the documents close the task.

Rule requirement

The bidder must accredit software for digital technical inspection, not merely mention software in general.

Evidence found

Annex 7 states the software claim and names API REST and JSON output.

Support requirement

The claim must be backed by supporting technical material.

Support found

The API matrix and module sheets connect SERVIU data requirements to named modules and outputs.

7
Produce the human-review packet
review output
Once the task closes, the agent writes a review packet for a human reviewer.
Provisional result
Pass
